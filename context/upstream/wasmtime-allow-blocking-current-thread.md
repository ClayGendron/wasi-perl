- **Status:** a draft for the owner to file, 2026-11-24. The owner decided: "Record this, I will do the issue filing later." Nothing here has been sent anywhere.

## 1. An issue and a PR for bytecodealliance/wasmtime

**Title:** C API: expose `WasiCtxBuilder::allow_blocking_current_thread`

**Body:**

> Under the C API, every blocking WASI file operation goes through tokio's `spawn_blocking`: it is handed to a background thread and waited for. `WasiCtxBuilder::allow_blocking_current_thread` turns that off. The CLI's `run` command sets it unless a timeout is given (`-W timeout=...`), since a call that blocks the thread cannot then be cancelled. The C API has no way to set it, so every C API embedder pays the hand-off, wasmtime-py included.
>
> On one x86-64 Linux VM with wasmtime 51, µs per call, the median of 7 runs of 20,000 calls each:
>
> | call | C API | C API with the flag (a local patch) | CLI, no timeout |
> |---|---:|---:|---:|
> | `fd_read`, 1 byte | 26.7 | 0.47 | 0.33 |
> | `fd_read` at end of file | 26.7 | 0.42 | 0.28 |
> | `fd_filestat_get` | 50.8 | 0.72 | 0.59 |
> | `fd_fdstat_get`, a file | 54.6 | 0.52 | 0.42 |
> | `path_filestat_get` | 57.0 | 1.24 | 0.94 |
> | `path_open` + `fd_close` | 34.1 | 1.49 | 1.23 |
>
> With the flag, `futex` calls per file operation drop from 4.9–18.4 to at most 0.2, and the process keeps 9 threads instead of 15–19.
>
> The patch adds `wasi_config_allow_blocking_current_thread(wasi_config_t*, bool)` to `wasi.h` and `crates/c-api/src/wasi.rs`. It forwards to the builder, and it is opt-in, so no existing embedder changes.
>
> One ordering detail: a preopen keeps the blocking mode it was made with. So the setter must be called before `wasi_config_preopen_dir`, and the doc comment says so. Applying the flag whatever the order would need the C API to keep the preopens until `wasmtime_context_set_wasi`. That would move the moment a bad folder is reported, so it is left to the maintainers.
>
> A question for maintainers: should the C API's synchronous path default to on? Nothing can cancel a synchronous host call there, which is the CLI's reason for its own default.

**The patch:** `c-api-allow-blocking-current-thread.patch`, 19 lines, against wasmtime 51's `crates/c-api`.

## 2. An issue for bytecodealliance/wasmtime-py, after (1) is released

**Title:** `WasiConfig`: expose `allow_blocking_current_thread`

**Body:**

> wasmtime's C API now has `wasi_config_allow_blocking_current_thread` (link to the merged PR). Could `WasiConfig` gain a setter for it?
>
> The change is about 10 lines:
> - the binding in `_bindings.py`, regenerated by `ci/cbindgen.py`;
> - a property in `_wasi.py`, documented as needing to be set before `preopen_dir`.
>
> It takes a guest file call from 26.7–57.0 µs to 0.42–1.49 µs, by kind of call. A guest program that opens and reads 100 small files goes from 36–39 ms to 2.3–3.0 ms.

## 3. What wasi-perl does when it ships

This follows the memo's §4.1:
- Move the wasmtime-py pin to the first release that has the setter.
- Set the setter in `runner._set_up` before the first `preopen_dir`.
- Add a slow check that counts `futex` calls per file call under `strace -c`: at most 0.2 with the flag. The check counts calls, so it holds on any machine.
- Leave fuel and outputs unchanged, so no golden output moves.

This needs a specification of its own when the release exists.
