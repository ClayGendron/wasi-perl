### Results that hold

- **Message, eval, exit 255, no trap.** Each refusal was run uncaught and inside `eval`: `exec "true","a","b"`, `exec { "x" } "x"`, `system { 'x' } 'x'`, `open(F, "|-")` and `open(F, "-|")` with no command, `qx` in list context, `CORE::readpipe` called from a `CORE::GLOBAL::readpipe` override, `kill 0, $$`, `kill 9, $$` in a string eval, `@SIG{qw(INT TERM)} = …`, `%SIG = (INT => sub {})`, a store inside `local %SIG`, and `system` inside a `sort` block. Each gives the right `<what>` and ends with 255 through `__wasi_proc_exit`. A `$SIG{__DIE__}` hook sees the refusal. An override of `readpipe` that does not call the core one works as natively. EXECUTED.
- **What still works.** `$SIG{__WARN__}` and `$SIG{__DIE__}`, assigned one at a time or through `@SIG{qw(__WARN__ __DIE__)}`, and set inside `local %SIG`, match native. So do `%SIG = ()`, `local %SIG`, `$SIG{ZERO}` and `$SIG{2}` (with the native warning). After a refused `$SIG{INT} = sub {}`, `$SIG{INT}` exists and is undefined. It reads as the truth: no handler was installed. EXECUTED.
- **The `Perl_apply` wrap leaves the other users alone.** `unlink`, `utime`, `chmod()` and `unlink()` with no arguments match native. `chmod` returns 0 with `ENOSYS` (wasi-libc has no `chmod`). `chown` dies "unimplemented" (`d_chown` is undef in `config.sh`). The wrapper forwards both to `__real_Perl_apply`. Both are 001 facts, not this change's. EXECUTED; `recipes/sandbox-refusals.c:123-128` READ.
- **Exit statuses.** ENOENT 2, EEXIST 17, ENOTDIR 20, EISDIR 21 and EINVAL 22 (`truncate $f, -1`) match native. So does EBADF 9, from a second `close STDOUT`. ENOTTY 25 is covered by the check the landing notes describe. `$! = 256; die` ends with 255, as natively. `END { print $? }` after a die from errno prints 2 on both sides. EXECUTED. I could not trigger ENOSPC, EPIPE or EACCES from a one-liner here; their rows match glibc's numbers. The wrapper computes the status the way `perl.c:5488-5509` does. It differs only in the text of the `PERL_EXIT_WARN` warning, which only an embedder can turn on. READ.
- **The exit mask.** `exit 256` ends with 0, `-1` with 255, `300` with 44 and `511` with 255, matching native. `recipes/wasi-stubs.c` masks the status before storing it, so the export answers 0 to 255, or -1 if the program never exited. EXECUTED (tests) and READ.
- **The 001 fixes.** M1: `WASI_SDK=/bogus recipes/wasi-cc --version` runs the pinned clang 23.1.0. EXECUTED. M2: a fake `wasm-opt` placed first on `PATH` runs on a plain `clang -O2` link and does not run with `--no-wasm-opt`. EXECUTED. The `producers` section of the module names only clang. M4: the CLI hello check grants only a throwaway `dev/`. L10: `assert_exit_refused` checks the innermost frame and the exact cause. L11: the 001 text is corrected, and `>&` is documented. READ.
- **Tests.** None was weakened. The changes to `test_perl_wasm.py` make its checks stricter (`assert_exit_refused`) or narrow a grant. READ.
- **The common `dup2` paths.** These all match native: a plain reopen of STDOUT, STDERR or STDIN onto a file, twenty reopens of STDOUT in a loop, a reopen after unflushed output, a reopen onto a missing directory (it fails and leaves STDOUT intact), a second close of the moved handle, and a reopen while another handle is open. EXECUTED. The `close` wrap is safe for every descriptor: it changes nothing unless the close is of the one remembered number *and* fails with EBADF, and it clears that number at the first close of it. READ (`recipes/sandbox-refusals.c:227-239`).

| H1 | High | `recipes/sandbox-refusals.c:212-220`; spec decision 8 (`003-…md:22`); `docs/sandbox.md:61-62` | **The `dup2` move destroys a descriptor that another Perl handle still owns.** Decision 8 says the only `dup2` callers left are `S_openn_cleanup` with a fresh descriptor, plus the child side of a fork. That premise is false for the fdopen forms (`&=`). `open STDOUT, '>&=', $h` and `open STDERR, '>&=STDOUT'` reach the same `dup2(fd, savefd)` (`doio.c:1070`) with `fd` shared with `$h` or STDOUT (`was_fdopen`, `doio.c:826`, `:1103-1117`). The move then takes the descriptor away from the other handle. The results, EXECUTED: `open STDERR, ">&=STDOUT"` reports no error. Every later `print STDOUT` is lost, and the run ends with exit 1, "Unable to flush stdout: Bad file descriptor". With `open(STDERR, ">&=", \*STDOUT)`, the open succeeds, stdout output is lost, and the exit status is 0. `open STDOUT, ">&=", $h` succeeds, and every later write through `$h` is lost (the file holds "via stdout" but not "via h"; `close $h` fails EBADF). The 2-argument `">&=" . fileno($h)` form reports "Not supported", yet it has already moved `$h`'s descriptor. On the 001 build, all of these failed cleanly with "Not supported", and both handles kept working (EXECUTED). So this is a regression from an honest `open` failure to silent loss of output. A fresh reopen has exactly one owner, so it still works. ## Verdict

Does not land: H1 is a regression introduced by decision 8. `open` with `&=`, which failed honestly on dev, now often reports success and takes the descriptor away from STDOUT or another handle, and later output is lost without an error. The fix is one check in `__wrap_dup2` (move only a descriptor with one PerlIO owner) plus four checks. With H1 fixed and M1 fixed or answered in writing, everything else here lands: every refusal in decision 1 behaves as specified in all the forms I tried, the errno table is exact, the exit mask is right, and 001's M1, M2 and M4 are fixed.
