# Libraries for agent workloads: where Perl is slow over vfs, and which modules to link

- **Status:** research, 2026-11-24. Study F of the speed research phase (`2026-11-24-perf-research-plan.md`). It changes no code on `dev`. The prototype's build changes are diffs in the evidence folder, not commits to `recipes/` or `scripts/`.
- **Researcher:** an agent (Claude Opus 5.5), branch `research/perf-libs`.
- **Stands on:** `2026-11-24-wasi-perl-against-wasi-python-on-speed.md` (the baseline and its harness) and specification 002 (how XS modules are linked statically).
- **The question:** where is Perl slow at what agents do over vfs, and which modules, linked statically, would close the gap at an acceptable cost?
- **Evidence:** `2026-11-24-perf-libs/`. The corpus is `corpus.py`; every raw number is in `results/`. Every number below is EXECUTED from those files unless it is labelled otherwise.

Labels: EXECUTED means run and seen. READ means read from a file. INFERRED means the researcher's reasoning.

Terms, once:

- **Fuel** is the guest's executed WebAssembly instructions. It is a count, the same on any machine, and it is the primary evidence here.
- **XS** is Perl's C extension interface. An XS module has a C half that must be linked into `perl.wasm`, because the guest cannot load code at run time.
- **Pure Perl** means the module is only `.pm` files. It needs no build: it is a file in the library folder.

## 1. The answer

The modules that pay are the ones that replace a pure-Perl parser with C. Four of the candidates build for `wasm32-wasip1` unchanged, with no patch, and add 298 KB (3.2%) to `perl.wasm` together.

| lever | before | after | gain | perl.wasm cost |
|---|---|---|---|---|
| **Cpanel::JSON::XS** (decode 1.4 MB) | JSON::PP: 1,350 ms, 11,157 M | 46 ms, 372 M | **29×** in time, 30× in fuel | +69 KB |
| Cpanel::JSON::XS (encode 20,000 rows) | 446 ms, 3,917 M | 64 ms, 580 M | 7× | (same) |
| **Text::CSV_XS** (50,000 quoted rows) | Text::ParseWords: 1,376 ms, 18,256 M | 152 ms, 1,525 M | **9×**; 2.5× over a hand regex | +55 KB |
| **YAML::XS** (2,000 records) | CPAN::Meta::YAML: 159 ms, 1,579 M | 30 ms, 174 M | **5×** in time, 9× in fuel; 63× over YAML::PP in fuel | +158 KB |
| Sort::Key (200,000 lines by a numeric field) | Schwartzian transform: 885 ms, 5,943 M | 307 ms, 2,783 M | 2.9× in time, 2.1× in fuel | +15 KB |

Sources: `results/fuel-base.json`, `fuel-A.json`, `fuel-B.json`, `wall-A.json`, `wall-B.json`, `sizes-A.json`, `sizes-B.json`.

With Cpanel::JSON::XS, wasi-perl decodes JSON faster than wasi-python's C `json` (46 ms against 61 ms, 372 M against 492 M instructions). Without it, wasi-python is 22× faster.

Three other findings matter more than any library for vfs, and belong to other studies:

1. **Multi-file programs are dominated by the host, not the guest.** A grep with context over 2,000 files takes 804 ms in wasi-perl against 29 ms natively (28×), for 422 M instructions, about 50 ms of guest work. `File::Find` over the same tree takes 396 ms against 11 ms natively (35×). wasi-python is as slow (876 ms and 239 ms). That is study E's question (§7.1).
2. **Module loads cost more than many programs' work.** `-MCarp` costs 34 M instructions, `-MIO::Handle` 48 M, `-MJSON::PP` 88 M and `-MText::CSV_XS` 91 M, against 1.6 M for `-e 1`. On a 2 KB JSON file, the load is 85% of the call (§7.2). That is study D's question.
3. **`File::Find` dies when the call has no working folder:** "Can't cd to /: No such file or directory", exit 2 (§7.3).

No core module runs in pure-Perl mode where an XS path exists: every probed XS path is in use, as natively (§5).

## 2. The corpus

**The workloads** come from what agents run over vfs. vfs's program catalog (READ: vfs `context/research/studies/2026-10-15-agent-shell/02-program-catalog.md`) counts 67,446 pipeline segments of real agent shell use:

- `grep` with `-n`, `-r`, `-A`/`-C` and `--include`; `sed -n` ranges; `sort`, `uniq -c` and `wc`;
- awk forms such as `{print $N}`, sums and `!seen[$0]++`;
- jq path expressions and `select`;
- `diff -u`;
- in-place regex edits: 101 of the 110 `perl` uses are `perl -pi -e 's/…/…/'`.

The corpus writes each of these the way an agent writes Perl with the core library, and adds what agents reach for in scripts: JSON, CSV with quoted fields, YAML, `sprintf` reports, templating, `Data::Dumper`, `Storable`, `Digest::SHA`, `File::Find` and Unicode case folding.

**The inputs** (`corpus.py data`) are deterministic: no clock, and a fixed linear congruential generator instead of `random`.

| file | what |
|---|---|
| `t.csv`, `t.log`, `t.json` | the baseline's: 200,000 CSV lines (4.4 MB), 200,000 log lines (9.8 MB), a 1.3 MB JSON array of 20,000 objects |
| `small.json` | the first 30 of those objects, 1,790 bytes: one vfs row's worth |
| `q.csv` | 50,000 rows with quoted fields holding commas and doubled quotes (2.0 MB) |
| `words.txt` | 2 MB of English-like prose |
| `uni.txt` | 1 MB of mixed-script UTF-8: German, French, Greek, Cyrillic, Turkish dotted I, ligatures |
| `a.txt`, `b.txt` | a 5,000-line file and a copy with 100 edits |
| `tree/` | 40 folders of 50 files, 40 lines each: 2,000 files |
| `t.yaml` | a block-style YAML list of 2,000 records (152 KB) |
| `tpl.txt` | a one-line template with six `{{name}}` slots |

**How it was measured:**

- **Fuel:** `corpus.py fuel`, one metered call per program. The answers are compared with native perl's byte for byte (`report.py`).
- **wasi-perl wall time:** `corpus.py wall`. One warm process, a warm module cache, one warm-up call, then the median of 3 to 9 calls. `cwd="/data"` on every call (§7.3).
- **Native perl:** `corpus.py native`. The perf-base native perl 5.42.3 as a subprocess, median of 3 to 9 runs. The XS candidates were built for it from the same tarballs (`native_xs.sh`).
- **wasi-python 0.1.6:** `corpus.py py`, snapshot mode, only where the program is the same algorithm class with the standard library. Python has no CSV-free CSV parser to compare with ParseWords, and no YAML.
- Every wall-clock run and every build held `flock /home/user/wasi-perl-wt/machine.lock`. Builds used `WASI_PERL_JOBS=4`. The machine is 4 shared vCPUs, so wall times are secondary to fuel.

Python is faster on JSON, CSV, SHA-256 and Unicode folding, where its standard library is C. With Cpanel::JSON::XS, Perl takes JSON too.

### 4.1 Notes on each

**Cpanel::JSON::XS.**

- Its UTF-8 validator has x86 and NEON SIMD paths and a scalar one; on wasm32 the scalar one is compiled (READ: `utf8_range.c` lines 13–25 test `__x86_64__`, `__i386__` and `__aarch64__` only).
- **Behaviour differs from JSON::PP in one place agents may see:** a number held as a float with an integer value encodes as `5.0`, where JSON::PP writes `5`. So `json_encode` gives 1,155,561 bytes against JSON::PP's 1,135,561 (EXECUTED, `results/fuel-A.json`; `edge.pl` prints `[5,5.0,"5"]`). wasi-python writes `5.0` too.
- Its booleans are `JSON::PP::Boolean` objects, as JSON::PP's are (EXECUTED, `edge.pl`).
- **JSON::PP cannot use it transparently.** JSON::PP never delegates to an XS backend (READ: `JSON/PP.pm`). The selectors behave differently:
  - JSON::MaybeXS tries Cpanel::JSON::XS first, so `use JSON::MaybeXS` gets it: 411 M.
  - JSON.pm tries JSON::XS, then JSON::PP. It never picks Cpanel::JSON::XS unless the environment says `PERL_JSON_BACKEND=Cpanel::JSON::XS`: 11,169 M without it, 396 M with it.

  Both selectors are pure Perl and not in core (EXECUTED: `json_decode+maybexs`, `json_decode+json`, `json_decode+json_cpanel`).

**Text::CSV_XS.**

- It is the parser behind Text::CSV, which uses it when present (1,527 M with it against 32,365 M without).
- Its load is 91 M, more than JSON::PP's, because it loads IO::Handle (§3.2). For a small CSV file the load dominates.

**YAML::XS.**

- make_ext.pl finds an extension by turning its `static_ext` name into a folder name. The XS module is `YAML::XS::LibYAML`, in a subfolder of the distribution, so the tarball unpacks as `cpan/YAML-XS-LibYAML` and `static_ext` names `YAML/XS/LibYAML` (READ: `make_ext.pl` lines 239–268, `Makefile.SH` lines 236–245; EXECUTED: the build).
- `$YAML::XS::LoadBlessed` is off: `!!perl/hash:Foo` loads as a plain hash (EXECUTED, §9).

**Sort::Key.** It takes a key extractor and sorts in C. The win is 2.1× over a well-written Schwartzian transform, and 11× over a naive comparator that splits in the block (30,403 M, §6). The Schwartzian transform alone gets 5.1× of that.

**JSON::XS.** Its `Makefile.PL` starts with `use Canary::Stability`, a configure-time module of its author's that is not in core (EXECUTED natively: "Can't locate Canary/Stability.pm"). It would need two more pure-Perl prerequisites at run time, common::sense and Types::Serialiser (READ: `XS.pm`). Cpanel::JSON::XS is its fork with the same interface, and it builds unchanged. Not attempted for the guest.

**List::MoreUtils::XS** and **Unicode::UTF8** both probe the compiler from `Makefile.PL`. In Perl's own build, `Makefile.PL` runs under miniperl, which can load no XS: one fails on IO, the other inside ExtUtils::CBuilder. Making them build means a hints file or a patch to their `Makefile.PL`. That was one attempt each; neither was retried, because neither pays:

- List::Util, already linked, has `uniq`, `any`, `all`, `none`, `pairs`, `zip` and `mesh`.
- Unicode::UTF8 is 1.7× over the `utf8::decode` builtin, natively.

## 5. Core modules in pure-Perl mode

`xs_probe.pl` asks, for 21 core functions that have a C path, whether the C path is the one in use (`B::svref_2object(\&f)->XSUB`). Under native perl and wasi-perl the 21 answers are identical: `results/xs-probe-native.txt` and `xs-probe-wasm.txt`, `diff` shows only the `static_ext`/`dynamic_ext` lines. EXECUTED. The probed functions:

- Data::Dumper's `Dumpxs`, with `Useperl` 0;
- File::Spec::Unix's `canonpath`, `catfile` and `catdir`, which PathTools implements in C;
- Cwd's `getcwd` and `abs_path`;
- List::Util, Scalar::Util, Storable, Digest::MD5, Digest::SHA, MIME::Base64, Encode, Unicode::Normalize, Time::HiRes and POSIX.

Every one is XS in both.

- **What is pure Perl is pure Perl natively too:** JSON::PP, Time::Local, Hash::Util's wrappers. Math::BigInt uses Math::BigInt::Calc by default in both, though Math::BigInt::FastCalc is linked. That is upstream's default, not a wasi-perl gap.
- **The core XS modules missing from the static set** are threads, threads::shared, IPC::SysV, Sys::Syslog, DB_File, GDBM_File, NDBM_File, ODBM_File, PerlIO::mmap, XS::APItest and XS::Typemap (`docs/modules.md`). None has a pure-Perl fallback that a program would silently slow down to. A `use` of one fails with "Can't locate" (READ: `docs/modules.md`; INFERRED for the fallback: none of their `.pm` files has one).

So no core module is slower in the guest because its XS half is missing.

|---|---|---:|---|---:|---:|
| count matches in a 9.8 MB log | `-ne '$n++ if /ERROR/'` | 565 / 116 | `-0777 -ne '$n++ while /ERROR/g'` | 117 / 65 | 4.8× |
| | | | `-0777 -ne '$n = () = /ERROR/g'` | 130 / 63 | 4.3× |
| substitute everywhere | `-pe 's/ERROR/WARN/g'` | 837 / 317 | `-0777 -pe 's/ERROR/WARN/g'` | 150 / 223 | 5.6× |
| sort lines by a numeric field | `sort { (split /,/, $b)[2] <=> (split /,/, $a)[2] } <>` | 30,403 / 2,510 | Schwartzian transform: `map {$_->[1]} sort {…} map {[(split /,/)[2], $_]} <>` | 5,943 / 690 | 5.1× |
| | | | Sort::Key's `rnskeysort` | 2,783 | 10.9× |
| parse CSV with quotes | `Text::ParseWords::parse_line` | 18,256 / 1,376 | a `\G` regex | 3,549 / 376 | 5.1× |
| | | | Text::CSV_XS | 1,525 / 152 | 12× |
| sum a column | `-F, -lane '$s += $F[2]'` | 1,269 / 148 | `-ne '$s += (split /,/)[2]'` | 1,170 / 137 | 1.1× |
| | `-ne '$s += $1 if /^\d+,[^,]*,(\d+)/'` | 1,670 / 160 | | | (the regex is the slowest) |
| filter lines | `-e 'print grep { /worker3 / } <>'` | 913 / 140 | `-ne 'print if /worker3 /'` | 570 / 121 | 1.6× |
| distinct values | `uniq map { (split)[1] } <>` | 2,014 / 216 | `-ne '$n++ unless $s{(split)[1]}++'` | 1,695 / 213 | 1.2× |
| UTF-8 round trip | `Encode::decode`/`encode` | 1,714 / 133 | `utf8::decode`/`utf8::encode` | 854 / 60 | 2.0× |
| JSON | `use JSON::PP` | 11,157 / 1,350 | `use Cpanel::JSON::XS` (if linked) | 372 / 46 | 30× |

Sources: `results/fuel-base.json` and `wall-A.json`, the `idiom_*` entries and the programs above. EXECUTED.

What to tell agents:

- **Slurp with `-0777` when the work is one regex over the file:** counting, `s///g`. It runs 4 to 6× fewer instructions than `-n`/`-p`, because the per-line loop, not the regex, is the cost.
- **Do not slurp when the work is per record.** Summing a column costs the same either way (1,318 M slurped against 1,170 M with `split`). `split` beats a capturing regex for fields.
- **Stream, do not build lists.** `print grep {…} <>` and `uniq map {…} <>` read the whole file into a list first, and cost more than a `-n` loop.
- **Never call `split` inside a `sort` block.** Use a Schwartzian transform (5×), or Sort::Key if it is linked.
- **Text::ParseWords is not a CSV parser.** It is 5× slower than a regex, and it drops doubled quotes: `parse_line(",", 0, q{a,"said ""hi"" x",b})` gives `said hi x` where CSV means `said "hi" x` (EXECUTED natively). The corpus sums only fields without doubled quotes, so its answers agree.
- **The `-n` variable trap.** Inside `for (1 .. 20) { … $_ … }`, `$_` is the loop counter, not the line. The corpus's first UTF-8 program made this mistake and printed 31 (EXECUTED, then fixed). Agents make the same one. Also, a regex run inside a loop body resets `$1`, `$2` and the rest: the corpus's first CSV regex read `$4` after an `s///r` and summed the wrong field (EXECUTED: 18,698,280.03 against 25,015,654.65, then fixed).

## 7. Other findings, for other studies

### 7.1 Per-file cost dominates multi-file programs (for study E)

| program | files | guest fuel | guest compute at about 8.5 B instructions/s | wall | host share |
|---|---:|---:|---:|---:|---:|
| grep_context | 2,000 opened and read | 423 M | about 50 ms | 804 ms | about 750 ms: **0.38 ms a file** |
| file_find | 2,040 entries stat'd, 40 folders entered | 134 M | about 16 ms | 396 ms | about 380 ms: **0.19 ms an entry** |

The fuel and the wall are EXECUTED. The compute rate is the baseline memo's (0.60 B instructions in 71 ms); the split is INFERRED.

wasi-python pays the same: 876 ms and 239 ms. So the cost is in the host's WASI path (wasmtime-py's preview1 implementation, or the runner), not in Perl. No library helps here, and vfs's mount layer will add a provider call per file on top.

Large outputs show a similar host cost. `-0777 -pe 's/ERROR/WARN/g'` runs 150 M instructions (about 18 ms) but takes 223 ms to read 9.8 MB and write 9.8 MB of stdout (INFERRED from the same rate). Counting over the same file with no output takes 63 ms. So reading 10 MB costs about 45 ms and writing 10 MB of captured stdout about 150 ms (INFERRED, for study A).

### 7.2 Module loads (for study D)

A program over one small vfs row pays mostly for its `use` lines. `json_small` (1,790 bytes):

- with JSON::PP: 103 M instructions, 29 ms, of which the load is 88 M;
- with Cpanel::JSON::XS: 37 M, 16 ms, of which the load is 36 M.

Carp alone is 34 M (EXECUTED, §3.2). A snapshot with common modules preloaded, or a lighter Carp path, would pay on every such call (INFERRED). Linking Cpanel::JSON::XS halves this call even before the parser matters.

### 7.3 File::Find needs a working folder (for the runner, or docs)

`File::Find::find` remembers the working folder and changes back to it at the end. With no `cwd`, the runner leaves the guest at `/`, which no grant serves. `find` then does its work and dies at the end with "Can't cd to /: No such file or directory", exit 2. With `cwd="/data"`, or with `no_chdir => 1`, it works (`file_find_cwd.py`, `results/file-find-without-cwd.txt`, EXECUTED). An agent's `find(sub {…}, ".")` is the common form, so vfs should always set `cwd`. The docs should say so too.

The ranking is INFERRED from the numbers above.

**Security, in general.** The four linked modules add C code that parses untrusted input. The guest's imports are unchanged: 32 functions, all `wasi_snapshot_preview1`, identical in base, A and B (`imports.py`, EXECUTED). So whatever a bug in that C code does, it does inside the guest's linear memory: a wrong answer, a Perl error or a trap. It reaches no host resource the guest could not reach before (INFERRED from the import list and WebAssembly's memory model).

The hostile-input probe `edge.pl` gives the same results in the guest as natively (`results/edge-*.txt`, EXECUTED):

- JSON nested 100,000 deep, truncated, with a NUL, with trailing garbage;
- a 5,000-digit number and invalid UTF-8;
- unterminated and misplaced CSV quotes, a NUL field, a 1 MB field.

Each case ends in a Perl error the program can catch, or in a result.

**Maintenance.** Each module is one line in a recipe list and one pin. Its version moves with a hash change. The build's warning count rises from 332 (base) to 519 (A) and 749 (B) (`grep -c warning:` of `20_target.log`, EXECUTED). The warnings are the modules' own, with `-Wall -Wextra`. None is an error under `-Werror=int-conversion`.

## 9. The prototype

The build change is small and adds no patch to Perl:

- `recipes/cpan-extensions`, new: one line per distribution, the tarball and the folder under `cpan/` it unpacks as.
- `scripts/20_target.sh`: after the patches step, it checks each listed tarball against `downloads/SHA256SUMS` and unpacks it into the Perl tree's `cpan/` folder. It refuses a tarball that is not pinned, does not match, does not unpack to one folder, or would replace a folder already there.
- `recipes/config.sh`: the module names are appended to `static_ext`, `extensions` and `known_extensions`. Perl's own `make_ext.pl` builds them as static extensions, and the generated `perlmain.c` registers them, exactly as specification 002 does for the core's.
- `downloads/SHA256SUMS`: one pinned line per tarball, with its CPAN URL.

The two diffs are `prototype-json-csv.diff` (set A) and `prototype-four-modules.diff` (set B), against `32dfb73`. The worktree was put back to `32dfb73` after the builds, so the branch carries the diffs as evidence only.

What a specification would still have to decide (INFERRED):

- The stamp of `20_target.sh` should hash the listed tarballs. It hashes the recipe list, and only the pins in `downloads/SHA256SUMS` protect the bytes.
- Whether `30_library.sh` should strip POD from the new `.pm` files: Cpanel's `XS.pm` is 97 KB, mostly POD.
- Where the pure-Perl companions (JSON::MaybeXS, Text::CSV, Algorithm::Diff) come from. Today the library is only what `installperl` installs. They would be one more recipe list, copied into `lib/perl5/5.42` and covered by `MANIFEST`.
- Checks in `tests/build/`: each new module loads, does one real thing, and is equal to native on `edge.pl`.
- `docs/modules.md` gains a "From CPAN" section with versions and licences.

## 10. Limits

- One x86-64 Linux machine with 4 vCPUs shared by six study agents. Wall times can carry interference despite the lock. Fuel does not.
- Each wall time is the median of 3 to 9 calls. Differences under about 10% are not meaningful.
- The native rows come from a subprocess, so they include about 2 ms of process start. The wasi-perl rows include the runner's per-call cost, about 4 ms.
- Some Python programs are a different algorithm, and are marked by the module they use: `csv`, `difflib`, `os.walk`, `pprint`, `pickle`. Python has no ParseWords or YAML counterpart, so those rows have none.
- The corpus's inputs are synthetic. Real vfs rows are smaller on average, which makes module load cost (§7.2) matter more and parser speed less (INFERRED).
- The compiled module cache's growth from the new modules was not measured. It should be in proportion to the code: about 3% (INFERRED).
